# Meeting Transcript → Ticket AI Flow

### 1. Goals & Constraints

- **Goals**: As soon as a meeting transcript is available, automatically run AI to **propose new tickets and possible updates** using the existing ticket-draft + human-approval model.
- **Constraints**: Reuse current ticket AI stack (`TicketDraftingService`, `TicketDraft`, `ChatSession`, OpenAI client, prompts) and keep the first implementation **simple, robust, and easy to extend**.

### 2. Reuse Existing Ticket AI Infrastructure

- **Core reuse**:
- `TicketDraftStructured`, `TicketDraftingContext`, `TicketDraftingService` in `backend/app/services/ticket_ai.py`.
- Ticket generation prompt in `backend/app/prompts/ticket_generation.py` (same schema and rules for tickets, plus `source_meeting_id`/`source_summary`).
- Draft persistence & accept/reject flows in `backend/app/api/routes/ai.py` and models `TicketDraft`, `TicketSourceLink`, `ChatSession`, `ChatMessage`.
- **Design principle**: Treat "meeting transcript" as **another input source** that feeds the same ticket-drafting pipeline, via a thin adapter that turns a transcript into a `conversation` + `TicketDraftingContext`.

### 3. Backend Pipeline: Transcript Ready → AI Ticket Drafts

- **3.1. Trigger when transcript is ready**
- Hook into the existing Recall/meeting sync flow (`recall_meetings_sync.py` / `meeting_monitor.py`) where a meeting transitions to "transcript available".
- From there, enqueue a background task like `process_meeting_transcript_for_tickets(meeting_id)` to keep the operation async and resilient.
- **3.2. Create or reuse a chat session for the meeting**
- In the task, ensure there is a `ChatSession` with `source_type="meeting"` and `source_id=meeting.id` (create it if missing) so the meeting AI run is modeled as a chat session.
- This allows reuse of `ChatMessage`, `TicketDraft` and the existing accept/reject endpoints with minimal changes.
- **3.3. Load transcript and build AI input**
- Fetch `RecallMeeting` + related `TranscriptSegment`s (ordered by time) for the given `meeting_id`.
- Concatenate segments into a single text block, optionally truncating to a safe max length (e.g., N characters/tokens) for v1; keep the truncation logic in a small helper so it’s easy to swap for a smarter chunking/summarization strategy later.
- Build a **single synthetic user message** like: "Here is the transcript of meeting X (date, participants). Extract and propose actionable tickets and updates following the usual rules. Transcript: ...".
- Load workspace labels and any relevant existing tickets (e.g., tickets already linked to this meeting via `TicketSourceLink`) to populate `TicketDraftingContext` similar to the chat flow.
- **3.4. Call `TicketDraftingService`**
- Use exactly the same `TicketDraftingService.generate_drafts(conversation, context)` with:
- `conversation`: `[ {"role": "user", "content": transcript_with_instructions} ]` or include a short synthetic assistant intro if helpful.
- `context`: `TicketDraftingContext(group_name, existing_labels, attached_ticket_summaries, max_tickets)`.
- Rely on the existing `ticket_generation` prompt and JSON schema to ensure consistent `TicketDraftStructured` outputs, including `source_meeting_id` and `source_summary` fields.
- **3.5. Persist drafts linked to the meeting**
- Create a `ChatMessage` for the synthetic user input and a `ChatMessage` for the AI assistant reply (using `result.assistant_reply`) under the meeting’s `ChatSession`.
- For each `TicketDraftStructured` in `result.drafts`, insert a `TicketDraft` row:
- `session_id` = meeting session id.
- `meeting_id` = the Recall meeting id.
- `trigger_message_id` = synthetic user message id.
- `assistant_message_id` = assistant message id.
- `raw_proposal` = `result.raw_content`.
- `structured_payload` = `draft.model_dump()`.
- `status` = `"proposed"` and `model_name` = `result.model`.
- This mirrors the chat flow so the same accept/reject logic works unchanged.

### 4. Ticket Acceptance & Source Linking

- **Keep existing accept/reject endpoints**
- Continue to use `/ai/ticket-drafts/{draft_id}/accept` and `/reject` exactly as in the chat flow; they already:
- Validate `TicketDraftStructured`.
- Call `create_ticket_from_structured_payload` or `update_ticket_from_structured_payload`.
- **Source attribution for meeting-derived tickets**
- Extend the accept handler to set `TicketSourceLink.source_type` based on context:
- For drafts with `meeting_id` not null, use `source_type="meeting"` and `source_id=meeting_id`.
- Otherwise, retain `source_type="ticket_chat"`.
- Ensure `TicketDraftStructured.source_meeting_id` (populated by the prompt) is also stored in the `Ticket` (if desired) or at least available via `TicketSourceLink.context`.

### 5. APIs to Surface Meeting Ticket Drafts

- **List drafts for a meeting**
- Either:
- Add optional filters to the existing `/ai/ticket-drafts` endpoint (e.g., `?meeting_id=...`), or
- Add a thin wrapper endpoint `/ai/meetings/{meeting_id}/ticket-drafts` that queries `TicketDraft` by `meeting_id` and `status="proposed"`.
- Return `TicketDraftSummary` objects, same shape as chat drafts, so the frontend can reuse components.
- **Accept/reject from meeting UI**
- The meeting transcript page calls the list endpoint, renders drafts, and triggers the same `/accept` and `/reject` endpoints for user actions.
- No new acceptance logic is needed; only wiring from meeting UI to the existing AI routes.

### 6. Modularity & Extensibility for Future Sources

- **Introduce a source-agnostic adapter pattern**
- Define a small interface/protocol (even just a convention) for "ticket input adapters":
- Given a `source_type` and `source_id`, produce `(conversation, TicketDraftingContext, metadata)`.
- Implement the first adapter for `source_type="meeting"` (transcripts) that encapsulates:
- Transcript loading.
- Text pre-processing/truncation.
- Instruction wrapping around the transcript.
- Later, add adapters for Slack threads, docs, GitHub PRs, etc., all feeding the same `TicketDraftingService`.
- **Prompt modularity**
- For v1, reuse `ticket_generation.py` (generator archetype) to avoid complexity.
- When you want more precision, add a dedicated extractor prompt (e.g., `ticket_extraction.py` using `build_extractor_prompt`) that first extracts candidate items from transcripts, then passes them into the existing generator as structured summaries.
- Keep both prompts under `backend/app/prompts/` with clear naming so you can A/B test and evolve them independently.

### 7. Robustness, Observability, and Limits

- **Error handling & retries**
- Wrap the background transcript-processing task with robust error handling:
- Catch `OpenAIConfigError` and `OpenAIRequestError` and log with meeting id.
- Mark the meeting’s AI-processing status (e.g., `ai_ticket_status=failed`) for UI feedback and potential retry.
- **Input size & performance**
- Implement conservative truncation in v1 (e.g., limit transcript to X characters or first Y minutes) to avoid timeouts and huge prompts.
- Expose a clear TODO or configuration hook for upgrading to chunking/summarization later.
- **Logging & auditability**
- Rely on existing `TicketDraft.raw_proposal` + `structured_payload` for debugging.
- Optionally add lightweight metrics (counts of drafts/tickets per meeting, error counts) in your monitoring stack.

### 8. Implementation Order (MVP-first)

- **Step 1**: Wire the background trigger when a transcript becomes available and create/reuse a `ChatSession` for the meeting.
- **Step 2**: Implement the meeting → `conversation` + `TicketDraftingContext` adapter and call `TicketDraftingService` to generate drafts.
- **Step 3**: Persist `TicketDraft`s with `meeting_id` and confirm accept/reject works unchanged, adjusting `TicketSourceLink` for meetings.
- **Step 4**: Add a simple API endpoint to list meeting-specific drafts and hook it up to the meeting transcript UI.
- **Step 5**: Iterate on transcript pre-processing (truncation, then smarter chunking) and, later, consider adding a dedicated extractor prompt for better recall on long meetings.
